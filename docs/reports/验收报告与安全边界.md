# 第4题验收报告与安全边界说明

**项目：Local Terminal MCP｜版本：0.1.0｜日期：2026-11-18｜编写：Manus AI**

本 MVP 按已批准的一期范围通过功能验收：自动化测试 40/40 通过，真实 Cursor Agent 完成全部 7 个验收步骤，15 次 MCP 调用覆盖全部 9 种工具。这个结论证明终端能力及已列出的可靠性行为可用，**不代表它是安全执行沙箱，也不代表能够隔离恶意 Agent**。[1] [2]

## 1. 验收结果

自动化测试包含 15 项真实 Broker/PTY 测试、23 项事件存储测试，以及新旧两代 MCP 客户端的 2 个完整场景；3 个测试文件全部通过，耗时 28.77 秒。覆盖同一 shell 的 cwd/export 延续、交互输入、PID link、多读者重放、取消等待、断线重连、幂等重试、进程回收、日志故障、资源上限和中文输出分页。[1]

Cursor 端到端验收使用真实模型 Agent，而不是由测试脚本冒充客户端。它创建 PTY、执行命令、读取输出、按同一 PID 建立只读 link、resize、发送交互文本和 Enter、查询完成状态，最后 terminate 并释放两个 link。关键输出为 `MCP_CURSOR_OK` 和 `ECHO:cursor-ok`；命令可信退出码为 0，终止返回 `EXITED`、`remaining_pids=[]`，退出日志仍可读。测试 shell PID <SHELL_PID> 已退出，测试 Broker 也已停止。[2]

Cursor 会话为 `<CURSOR_SESSION>`，终端会话为 `<TERMINAL_SESSION>`。15 次调用均已从结果轨迹解析核对，未使用 Cursor 内置 shell 或其他 MCP 执行来代替本题工具。逐次记录不包含模型思考内容。[2]

验收适用于 macOS 本地、同一操作系统用户下的可信客户端，PID link 只针对本 Broker 已托管的 shell。Cursor 接入已实测；不能据此声称每一个 MCP Agent 都已适配。Manus 的本地自定义 stdio 接入尚未实测，公网 HTTPS、登录模块、任意外部终端接管和恶意客户端安全测试均不在本次通过范围。

## 2. 直接回答：任何 Agent 连上后，都能执行脚本吗？

**从当前服务端的授权逻辑看，基本是。** 只要这个 Agent 的本地调用实际到达本服务，客户端允许它调用工具，并且能够调用 `terminal_create` 与 `terminal_exec`，它就可以创建控制会话并提交任意 shell 代码。服务端不会按 Agent 名称、厂商、账户或脚本内容再次审批。[3] [4] [5]

这里不是“全世界任何 Agent 都可以从网络连进来”：当前没有 TCP/HTTP endpoint。它必须由本地客户端启动 stdio 网关，或通过拥有本机接入能力的本地程序连接 Broker。正常私有目录权限下，其他普通 macOS 账户不能直接访问这些路径；root 等高权限主体不在这种隔离承诺内。[3] [4]

也不是“连接成功立即无条件执行”：Cursor 等客户端可以在调用发送前拒绝某个工具，服务还有参数、会话状态和资源限制。但**一旦调用已经通过客户端并到达服务端，当前实现没有独立的脚本许可检查**。这套服务应被视为授予 Agent 一项以 Broker 启动用户和执行上下文运行的高权限终端能力，而不是只授权它执行项目里的几段脚本。

## 3. 实际有哪几层边界？

### 3.1 接入边界：本地操作系统用户，不是 Agent 身份

MCP 网关使用 stdio；Broker 只监听私有 Unix socket。启动时检查目录和文件所有者，目录设置 `0700`，socket 设置 `0600`，异常符号链接被拒绝。其主要效果是缩小本机接入范围，不是识别不同 Agent。[3] [4]

当前没有 OAuth、API Key 登录、Agent 白名单或按客户端身份执行的服务端角色策略。Broker 主连接也没有单独验证每个客户端的 peer UID；正常接入防护主要依赖私有目录的操作系统访问权限。MCP 客户端报告自己的名称，也不会因此获得不同授权。

同一 macOS 用户下的 Cursor、其他本地 Agent 和插件属于同一个信任域。服务不能把同 UID 的恶意程序与正常客户端可靠隔离；这些程序也可能直接访问本用户有权读写的代码、配置和日志。随机 handle 或控制通道 token 不应被当作针对这种对手的登录认证。

远程 Agent 本身不能直连这套本地 stdio 服务，但如果你让一个本地客户端或代理接收远程模型指令，它就可以代远程 Agent 调用本地工具。此时远程指令同样会获得这个执行能力。“不开放公网端口”不等于“模型指令不会来自云端”。

### 3.2 执行边界：Broker 的系统权限，不是 cwd

shell 由 Broker 创建，当前执行入口是 `/bin/zsh -f -i`。`command` 本来就是授权执行的 shell 代码，不会被转义成普通文本，也没有命令白名单。`cwd` 只检查它是不是存在的目录，没有项目路径 allowlist，更不是文件系统根边界。[5]

因此，Agent 可以切换目录，可以在服务进程有权限的位置读写或删除文件，可以启动解释器和其他程序；如果启动上下文允许联网，脚本也可以自行联网。服务的初始环境变量经过筛选，不是完整复制父进程所有环境变量，但这不构成文件或凭据隔离。

服务不会自动获得 root，也不会因为接入 MCP 就自动越过 macOS 现有的文件访问或其他系统控制。具体能访问哪些受保护目录，仍由 Broker 的运行账户、宿主执行上下文和已有系统授权决定，不能简单断言与某个 GUI 终端完全相同。如果将服务改成高权限运行，风险也会随之扩大。

最多 16 个活跃会话和日志预算，只限制服务自己的会话与记录量。它们不是脚本的 CPU、内存、派生进程数或外部文件写入配额，不能防止任意代码制造资源耗尽。

### 3.3 会话边界：防误操作和并发冲突，不是跨 Agent 隔离

只读 link 不能通过该 link 执行、写入或终止；控制 link 才能做这些操作。同一会话只有一个控制 link，忙碌时不接受新 exec；未托管 PID 不能通过 link 工具接管。[4]

但是，**一个只读 link 不等于一个永久只读的 Agent 身份**。当前任何具备 create 调用能力的连接都能新建终端，并自动拿到控制 link。服务没有“这个客户端只允许 read/status，禁止 create/exec”的独立身份策略。持有有效 handle 的请求也没有绑定到不可冒用的 Agent 主体。

同一用户下的其他客户端可以根据已托管 PID 创建读关联，查看该会话的保留输出；没有每个 Agent 独立的数据所有权 ACL。资源列表不主动枚举所有会话，只是展示策略，不能当作数据安全隔离。

`terminal_terminate` 的 PID 身份和进程关系检查用于减少误终止，不能限制任意 shell 代码的其他行为。例如，不支持通过 PID link 接管其他终端，并不等于 exec 中的程序不能访问或向同用户的其他进程发送通常允许的信号。

### 3.4 客户端审批边界：Cursor 的开关不是服务端策略

本次为无交互验收配置了 `.cursor/cli.json`，允许本题的 9 个 MCP 工具，同时拒绝 Cursor 内置 Shell、Write、WebFetch。这样可以验证功能确实由 MCP 完成，但它**不能禁止 `terminal_exec` 内部写文件或联网**。放行通用 shell 执行，就已经放行了这些操作通过 shell 实现的路径。[2] [6]

Cursor 的 `--force` 开关及其 `--yolo` 别名改变的是客户端执行审批；显式 deny 仍可能优先。它们不为本 Server 增加鉴权，也不自动绕过操作系统权限。其他 Agent 可以采用不同的审批策略，本服务无法要求它们都遵守 Cursor 的配置。

MCP 工具描述和 `readOnlyHint` 等注解也不是授权机制。服务端必须实际检查权限才算策略；当前主要检查的是 handle 的 read/control 类型，而不是客户端身份。[7]

## 4. 数据和撤销风险

终端日志是私有文件，但其中可能有源码、配置、测试数据、敏感输出或程序回显。服务不主动把日志上传到模型平台；然而 Agent 读到输出后，可能将其加入云端模型请求，脚本也可能主动传输数据。因此，日志的 `0600` 权限不能阻止获准执行的同用户 Agent 获取这些内容。

关闭 Agent 或 MCP 网关，只会断开连接，不会自动终止已经接受的命令。这个行为是已验收的持久会话能力，也意味着“客户端审批关闭”不等于“执行已经撤销”。需要明确 terminate 相关会话，或通过本地管理命令停止相同 runtime 的 Broker；后者会结束它托管的全部会话。对主动脱离或重新托管的程序，当前不提供容器式强收容保证。

本次 40 项自动化测试和 Cursor 验收不是安全渗透测试。未承诺恶意同 UID 对手隔离、完整数据防泄露、无条件无残留或抵抗所有系统级竞态。

## 5. 当前适用范围与下一步安全设计

当前版本适合你自己明确信任的本地 Agent，用于开发、测试和交互式终端工作。不要仅因为一个客户端支持 MCP，就把它视为可信；不要把本服务无认证转发到公网，也不要将任意第三方 Agent 放进与个人数据、凭据相同的执行环境。

如果你希望“不同 Agent 有不同权限”，首先应增加服务端身份与能力策略。明确控制谁可 create、谁可 exec、谁只能 read/status，校验每次操作，包括内部管理入口；只读角色不能通过 create 给自己升级。API Key 或 token 可以治理正常客户端，但单靠它们仍无法把同 UID 的恶意本地程序变成安全隔离对象。

如果你希望“即使 Agent 提交任意脚本，也只能影响指定项目”，更关键的是改变执行环境：使用低权限独立账户，或隔离的 VM/容器，只暴露必要项目目录，并限制网络出口与资源。权限策略必须同时作用于派生进程，而不只作用于 MCP 方法名。具体采用哪种方案需要单独设计和验收，目前没有实现。

如果只需要跑固定工作流，可以将通用 shell command 换成受控动作，例如由服务选择固定执行程序和参数。但仅允许 `python`、`node` 或 `bash` 这几个命令名称并不安全，因为解释器仍能执行任意代码。破坏性或跨项目动作还应有服务端审批和可追踪的执行记录，而不是只依赖提示词。

**最终判断：一期功能验收通过；它是可信本地用户的通用终端 MCP，不是多 Agent 安全执行平台。若要求“陌生 Agent 连上也不能任意操作本机”，当前实现还不满足，需要在服务端授权和执行隔离两个层面继续开发。**
