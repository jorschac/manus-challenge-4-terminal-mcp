# 第4个编程挑战：本地终端 MCP Server 技术方案

> 这是开发前的审批材料，保留当时的设计与状态。当前实现和验收已完成，请以任务完成报告及最终测试报告为准。

**审批稿 v1｜2026-11-18｜Manus AI**

建议一期实现一个**同一 macOS 用户下的本地终端托管服务**：MCP 客户端通过 stdio 网关调用，独立的本地 Broker 持有真实伪终端（PTY），负责会话存续、命令状态和可重放输出。登录、远程访问和公网部署均不实现。

这不是单次 `exec()` 的包装。终端有稳定 ID，同一个 shell 的工作目录和环境可以延续，交互进程可以继续接收输入，客户端断开后也能重新 link。需要你明确批准的三项解释是：**PID link 只针对本服务已托管的终端；exec 不向忙碌的前台程序强塞新 shell 命令；流式能力采用标准订阅通知配合增量读取，并为只支持 Tool 的客户端提供长轮询降级。**

本文是技术方案，不代表实现完成。当前仅完成官方资料核实和本机只读检查，尚未编写 Server、安装依赖、修改 Cursor 配置或执行集成测试。

## 1. 权限边界：无登录，但不是无安全边界

服务由普通 macOS 用户启动。调用方是该用户信任的本地 MCP 客户端或 Agent。客户端启动 stdio 网关，网关通过 Unix Domain Socket 连接本地 Broker。Broker 的目录权限为 `0700`，socket 和日志权限为 `0600`；启动时检查目录所有者、拒绝异常符号链接，并对已有 socket 做实际握手，避免并发启动多个 Broker。

一期不开放 TCP/HTTP 监听，不实现账户、OAuth 或跨用户授权，也不申请 root、sudo、辅助功能或完全磁盘访问权限。不使用公网隧道来“顺便兼容”云端 Agent。

**信任边界是 macOS 用户，而不是各个 Agent。** 同一用户下的受信任客户端可以重新 link 该用户的托管会话；不同 Agent 之间不提供安全隔离。不可猜测的 link handle 用于定位连接和防误操作，不是登录系统，也不能防御同 UID 的恶意进程。

子进程继承服务进程的操作系统权限。`node-pty` 官方也明确这一点。[1] 因此，限制初始 `cwd` 并不等于沙箱：任意 shell 命令仍可能读取用户有权访问的其他文件，或自行联网。服务自身不上传日志，但 Agent 取得输出后可能把它发送给其模型服务。接入终端 MCP 相当于授予这个 Agent 一项高权限本地执行能力。

## 2. 需求中需要澄清的四个地方

### 2.1 “根据 PID link”不能默认解释成接管任意终端

macOS 的 `openpty`/`forkpty` 创建主从两端，并将主端文件描述符交给创建者。PID 标识的是进程，不是 PTY 主端访问权。本机 `man 3 forkpty` 已核实这一机制；Apple 文档也描述了相同关系。[2]

所以，知道 Terminal.app、iTerm2 或 Cursor 集成终端里某个 shell 的 PID，并不意味着本服务能取回其 PTY 主端。打开 `/dev/ttysXXX` 从端也不是等价方案：不能可靠读取原来的输出，可能干扰现有程序，更不能找回之前没有记录的历史。

一期定义为：`terminal_link(pid)` 在 Broker 的托管注册表中找到这个 shell PID，校验进程身份后返回新的 link。客户端 A 创建终端，客户端 B 可以凭返回的 PID link 到**同一个**终端，而不是新建替代终端。任意未托管 PID 返回 `NOT_MANAGED`，不伪装成成功。

这是对“已有终端”范围的限制，需要你批准。如果你的硬性要求是“任意应用创建的现有终端都可完整读写”，当前方案不能满足。可以另行增加 tmux 或应用专用适配器，但前提是原终端本来由可合作的服务管理；一期不做调试器注入，也不接管普通 GUI 终端。本机 PATH 中暂未发现 tmux。

### 2.2 `docker exec` 与“向当前终端输入”不是同一种操作

`docker exec` 的类比只能保留“在既有上下文中启动命令”这一层含义。Docker 在容器里创建新进程；本题没有容器命名空间，也不能凭空在一个正在运行的 Python REPL 或 Vim 进程内部启动 shell 命令。

推荐提供两种明确操作：`terminal_exec` 在受控 shell 空闲时执行新命令，保留该 shell 的 `cd` 和 `export` 状态；`terminal_write` 把文本或按键送给当前前台程序。终端忙碌时，新 exec 返回 `SESSION_BUSY`，不隐式排队，不把 `ls` 塞进密码提示、REPL 或 Vim。

如果你实际需要的是“原交互进程继续运行，同时启动独立命令”，应另外创建终端，或以后新增独立进程执行模式。它不会完整共享原 shell 的内存状态。

### 2.3 长连接流式读取不能等同于无限 Tool 返回

普通 `tools/call` 是一次请求对应一个最终结果。不能保证所有 MCP 客户端都把一个无限不结束的 Tool 当作终端流来消费。当前 MCP `2026-07-28` 提供 `subscriptions/listen` 长连接，资源更新通知只是通知 URI 发生变化，不是任意终端输出分片的标准载荷。[3] [4]

一期同时提供两层：支持订阅的客户端保持标准长连接，收到终端日志更新通知后，按游标取回增量；只支持 Tools 的客户端调用有界 `terminal_read`，无输出时最多等待一段时间，再继续读取。

前者是“长连接通知 + 增量消费”，后者是长轮询，**不能把后者宣称成原生推送**。如果你坚持“同一条连接必须直接持续推送每个输出分片”，需另加自定义扩展或专用流接口，并接受它不是所有 MCP Agent 的共同能力。

### 2.4 “终止对话”要区分连接与进程

推荐把“终止会话”定义为结束指定 PTY 及其受管进程，即 `terminal_terminate`。另外提供 `terminal_unlink`，只释放当前 link，其他客户端和终端本身不受影响。MCP 网关退出同样不默认杀掉终端；停止整个 Broker 是本地管理命令，不作为容易误调用的 Agent Tool。

## 3. 推荐架构和技术栈

使用 Node.js 22、TypeScript、官方 MCP TypeScript SDK v2、`node-pty` 和 Zod。测试使用 Vitest 与 MCP SDK 客户端。`node-pty` 支持 macOS，提供创建 PTY、读取输出、写入输入和调整尺寸等能力。[1]

架构分成三个职责清晰的部分。

**MCP 网关**由每个客户端独立启动，负责协议协商、参数校验、Tool 和 Resource 适配。网关 stdout 只输出 MCP JSON-RPC，诊断写 stderr；PTY 内容绝不直接透传到网关 stdout。[5]

**本地 Broker**是同一用户共享的进程，独占持有 PTY 主端，维护会话、link、控制权和命令记录。网关断开不会丢失 PTY。Broker 与网关之间的私有 IPC 可以持续推送事件，但不要求普通 MCP 客户端理解这套内部协议。

**日志存储**按会话追加有序事件，用分段文件和索引保存。它负责游标续读和保留策略，而不是只保存最后一次 MCP 调用的输出。MVP 不引入数据库或 tmux 依赖。

会话统一使用服务生成的 `session_id`。`shell_pid` 用于符合题目的 PID link 与诊断；`link_id` 标识一个可读或可控制的关联；`command_id` 标识一次 exec；`cursor` 标识已消费到的事件位置。这些是应用层状态，均不依赖 MCP 传输层的 session ID。

这一点对新旧兼容尤其重要：最新 `2026-07-28` 规范已移除协议级 session 和 initialize 握手。[4] 推荐使用 SDK v2 的 `serveStdio(factory)` 入口支持新旧两代协议，而不是手工拼握手，也不是仅把旧 SDK 的包名换成新包名。官方文档明确 `serveStdio` 默认可服务两代客户端。[6] [7] 开发时锁定具体小版本和依赖，不在方案阶段假定安装结果。

## 4. 一期原子能力：9 个工具

### 4.1 `terminal_create`

创建一个受控 `/bin/zsh -f` PTY，并自动建立控制 link。输入包括 `cwd`、`cols`、`rows` 和可选环境覆盖。返回 `session_id`、`link_id`、`shell_pid`、TTY、状态、起始游标及能力标识。

一期默认无 GUI 窗口，也不加载用户的交互配置。创建后必须等 bootstrap 确认 ready 才报告 `IDLE`；失败时回收子进程并返回具体原因。需要登录 shell 或其他 shell 的支持作为后续扩展，而不是暗中执行用户配置。

### 4.2 `terminal_link`

必需参数是 `pid`，可指定 `access: read | control`。在托管表中解析 PID，校验 UID 和进程启动身份，返回新的 link 及同一个 session ID。一个会话允许多个读者，但只允许一个控制 link。

退出会话可以只读关联其保留日志，返回的状态明确是 `EXITED`；如果旧 PID 已被其他进程复用则拒绝，不关联到新进程。不默认支持任意子进程 PID，也不扫描所有终端并尝试抢占。

### 4.3 `terminal_exec`

输入是 `link_id`、shell `command`、`request_key` 和可选 `wait_ms`。只允许控制 link 在受控 shell 空闲时执行。`command` 是有意授权执行的 shell 代码，不是自动转义成普通参数的字符串。

每次调用先建立命令记录。短命令在等待预算内结束，就返回退出码和输出；长命令或交互程序返回 `command_id`、`RUNNING` 和当前输出游标，之后用 read、write、status 继续操作。推荐默认等待 2 秒，上限 10 秒；`wait_ms: 0` 表示提交后立即返回。

相同 `request_key` 与相同参数返回既有命令，不重复执行；相同 key 配不同命令返回冲突。等待超时或 MCP 断线不自动杀进程。执行结果里的非零 `exit_code` 是正常命令结果，不是 JSON-RPC 协议失败。

### 4.4 `terminal_read`

输入是 `link_id`、可选 `after_cursor`、`max_bytes` 和 `wait_ms`。返回有序 `events`、`next_cursor`、`earliest_cursor`、`has_more`、`eof` 和会话状态。推荐每次默认 16 KiB，上限 64 KiB；长轮询上限 20 秒，客户端可以设置更短预算。

同一游标重复读取允许重放相同事件，客户端按 `seq` 去重。多个读者互不推进对方的游标。游标超出保留范围时，明确返回 `CURSOR_EXPIRED` 和最早可读位置，不悄悄跳过缺失历史。

`eof` 只有在会话结束且保留数据已读完时为真；暂时没有输出、或某条命令已经结束，都不等于终端 EOF。

### 4.5 `terminal_write`

向当前前台程序发送文本或枚举按键，二者互斥。一期支持 Enter、Tab、方向键、Ctrl-C、Ctrl-D 等常用输入，并限制单次写入大小。

文本默认不自动附加回车。写入需要控制 link，返回“已送入 PTY”而不是承诺程序已经处理。Ctrl-C 是发送终端控制字符，能否触发中断取决于终端模式；Ctrl-D 也不是通用的“关闭进程”命令。所有输入写入都串行化，避免多请求交错。

### 4.6 `terminal_status`

带 `link_id` 返回会话状态和前台相关诊断；可额外带 `command_id` 查询某条命令的状态、退出码和输出水位。只读返回不修改会话。

状态能可靠区分“已退出”和“仍在运行”，但一期不承诺通用地识别“正在等密码”“正在等输入”或“程序卡死”。命令处于 `RUNNING` 不意味着它一定在消耗 CPU。

### 4.7 `terminal_terminate`

需要控制 link。先将会话标记为 `CLOSING`，拒绝新写入和 exec，再向已核实属于该会话的进程发送 SIGTERM，宽限期后对仍存活的受管进程升级 SIGKILL。推荐默认宽限期 3 秒。

重复终止返回当前终态，不误报成新的失败。终止后日志仍可读取。返回处理过的目标及清理结果，不能仅因为发送了一个信号就宣称所有进程已退出。

### 4.8 `terminal_unlink`

释放当前 link，取消其读等待和订阅，并释放控制权；不杀进程。操作幂等。客户端重连后重新 link，或继续使用尚未到期的显式 handle，不通过隐式“当前终端”猜测对象。

### 4.9 `terminal_resize`

调整 PTY 的列数和行数，需要控制 link，并校验合理范围。交互程序能据此重新布局。这项能力使服务更接近真正可用的终端，而不只是提供 stdin/stdout 管道。

上述 create、link、exec、read 和 terminate 对应题目要求的五项能力；write 和 status 补齐题干中的交互输入与运行状态；unlink 和 resize 消除生命周期歧义并改善 TUI 使用。

## 5. 如何可靠得到执行结果和连续输出

### 5.1 受控 shell 与命令边界

不能通过匹配 `$`、`%` 或“最后一行像提示符”推断命令完成。不同提示符、ANSI 控制序列、无换行输出都会使这种方案失效。

推荐 bootstrap 建立受控执行入口。命令保存在私有临时脚本中，在当前 shell 中 source，避免 subshell 导致 `cd`、`export` 丢失。命令 ID、开始、完成、退出码和实际 cwd 通过私有 IPC 控制通道回报；PTY 流使用每命令随机边界帧定位前台输出范围。边界解析器必须支持跨 chunk 分割，普通输出不能成为退出码的权威来源。

控制通道和 PTY 数据通道到达顺序可能不同。因此，“命令完成”与“输出已消费到哪里”分开记录，不能收到完成回调就截断尾部输出。边界帧用于正常前台任务的排序，不提供对恶意同 UID 程序的安全隔离。

如果命令执行 `exit`、用 `exec` 替换 shell，或破坏 bootstrap，服务可能无法收到正常完成回报。这时返回明确的 shell 退出、非受控或 `UNKNOWN` 状态；不会为了看起来成功而编造退出码。终端仍存活但控制协议失效时，只保留 read/write/status/terminate，后续 structured exec 返回 `SHELL_UNMANAGED`。

对 `cmd &` 等后台任务，exec 完成表示提交这条 shell 命令完成，不表示后台工作完成。后台输出可以与后续命令混合；会话日志完整记录观察到的流，但不承诺准确追溯每个字符属于哪个后台进程。

### 5.2 输出不是 stdout/stderr 两条独立管道

PTY 中程序的 stdout 和 stderr 通常连接到同一个终端，无法事后可靠拆开。返回统一 `output` 事件，不虚构独立的 stdout/stderr 字段。一期面向 UTF-8 终端文本，保留 ANSI 和控制字符，不承诺任意二进制传输或完整终端屏幕渲染。

每个事件包含 `seq`、时间、类型和数据。类型覆盖 output、command_started、command_completed、session_exit 等。输出事件受 chunk 大小限制，解析状态跨 chunk 保持，避免 UTF-8 或控制序列被错误处理。

### 5.3 回放、长轮询与标准订阅

Broker 对保留日志分配单调序号；read 按游标读取。实现长轮询时先登记等待者，再复查最新序号，消除“检查无输出到开始等待之间”的竞态。请求取消只撤销该等待者，不撤销正在运行的命令。

每个 link 可以获得一个终端事件 Resource URI。新协议客户端通过 `subscriptions/listen` 订阅 URI，旧协议客户端使用 `resources/subscribe`。服务合并高频更新通知，客户端再通过 terminal_read 或带游标的 Resource URI 获取数据。[3] [6]

订阅是唤醒机制，游标才是可靠续读机制。网关重启后需要重新订阅；不用 SSE event ID 或 MCP 协议 session 代替输出游标。最新 MCP 已移除协议层 SSE 重放机制。[4]

### 5.4 有界资源，而不是无限内存

推荐初始限制为最多 16 个活跃终端、每会话内存缓存 4 MiB、每会话磁盘日志 100 MiB、总日志预算 1 GiB，退出会话最多保留 7 天。这些是可配置产品默认值，不是性能实测结论。

慢客户端不阻塞 PTY 采集。日志按预算淘汰，缺口显式可见；磁盘写入积压和磁盘满采用有界降级并记录 gap，不能无限缓存或静默丢数据。提示词、命令和终端输出可能含秘密，默认审计日志不复制输入正文；终端回显仍可能把输入带入输出日志，不能承诺自动清除所有秘密。

## 6. 会话生命周期、并发和故障边界

会话状态采用 `STARTING → IDLE ↔ BUSY → CLOSING → EXITED`，另外保留 `UNMANAGED` 和 `LOST`。命令状态与会话状态独立：一条命令可以完成，而 shell 继续处于 IDLE。

一个会话只有一个控制 link，多读者各自持有游标。link 明确传参，不使用“当前会话”。控制权不强抢；原控制方 unlink 后，其他客户端可以获取控制 link。网关失联时，控制租约在短宽限期后释放，但 PTY 不终止。显式 link handle 有有界有效期，活跃调用可续期；读日志不应自动抢占控制权。

Broker 生命周期独立于客户端：存在活跃终端时保持运行；没有客户端且没有活跃终端时可延时退出。提供本地 `broker status` 和 `broker stop` 管理入口；stop 明确结束受管会话。测试结束会主动回收测试 Broker，而不是把它留在后台。开机自启、launchd 安装和系统级部署不在一期默认执行范围。

**网关重启与 Broker 崩溃不是同一种恢复。** 网关重启后仍能 link 同一个真实 PTY。Broker 崩溃则主端可能丢失，一期不承诺恢复原 live 终端。重启后保留已落盘日志，把相关会话标记 LOST，并对残留受管进程谨慎清理，绝不只凭磁盘里的旧 PID 重新宣称可控制。

对于执行请求，先记录幂等 key，再提交命令；不确定是否执行完成时返回 UNKNOWN，重复同一 key 不重新执行。进程崩溃跨越“已登记”与“实际开始”的窗口，无法无条件保证 exactly-once。方案承诺可识别的不确定性和避免盲目重跑，而不是伪造一次且仅一次的执行保证。

终止实现要考虑 shell 的前台作业可能使用不同进程组，不能只 `kill(shell_pid)` 或无检查地杀 `-shell_pid`。发送信号前核实 UID、启动身份、父子关系及进程组成员，避免误杀 PID 复用或无关进程。

对于主动 `setsid`、脱离会话或重新托管到别处的程序，一期只能尽力清理已跟踪的受管进程，不能给出容器级进程收容保证。验收覆盖普通 shell、前台交互程序及未主动脱离的子进程。

## 7. 对不同 MCP Agent 的适配结论

**不能保证适配所有“支持 MCP”的 Agent。** 可用性同时取决于传输、协议代际、宿主权限、工具结果限制、并发调用方式以及资源订阅支持。协议一致不意味着 Agent 一定会正确安排 exec/read/write。

对支持本地 stdio 的 Agent，一期有标准接入路径。所有核心能力都作为 Tools 暴露，并用简单 JSON Schema、显式 ID 和可操作错误描述。返回 `structuredContent` 的同时附带序列化文本，兼容只展示文本的客户端，这是官方推荐的向后兼容方式。[8]

对订阅能力较弱的 Agent，核心工具仍可工作，但需要 read 循环。实际交互测试应使用短等待或 `wait_ms: 0`，避免宿主串行执行一个长等待后，没有机会调用 write。

### 7.1 本机 Cursor：具备验证前提，但还没有验证通过

已核实本机存在 `cursor-agent`，版本是 `2026.02.13-41ac335`。CLI 支持 `mcp list`、`mcp list-tools`、`mcp enable` 等命令，也支持指定 workspace 和非交互输出模式。Cursor 官方文档说明 CLI 与编辑器共用 MCP 配置，支持本地 stdio。[9] [10]

特别注意：这台机器的 `agent` 命令指向 `<HOME>/.grok/bin/agent`，不是 Cursor。后续验证会明确调用 Cursor CLI 的绝对路径，避免测错客户端。

审批后只在独立验证目录创建 `.cursor/mcp.json`，不覆盖 `~/.cursor/mcp.json` 或其他挑战的配置。配置示意如下，路径会在实现后替换为实际值：

```json
{
  "mcpServers": {
    "local-terminal": {
      "type": "stdio",
      "command": "<Node.js 可执行文件的绝对路径>",
      "args": ["<本项目 dist/mcp.js 的绝对路径>"]
    }
  }
}
```

验证分为两层：先用 `mcp list-tools local-terminal` 检查协议连接和 9 个工具，再让 Cursor Agent 实际完成 create、exec、read、write、status 和 terminate。只看到工具列表不算端到端成功；需要检查调用轨迹，确认不是 Cursor 内置 shell 代做了这些动作。

只启用本次指定的 MCP，不使用全局 `--approve-mcps` 或 `--force` 来掩盖权限问题。若 CLI 未登录，模型驱动的测试需要你先完成 Cursor 登录；这与我们不实现 MCP 登录模块并不矛盾。当前没有查询或读取你的 Cursor 凭据，也不假定已有登录可用。

### 7.2 Manus：纯本地一期不能直接承诺公开连接器入口可用

Manus 官方 Custom MCP Servers 文档当前说明的是部署可访问 HTTPS endpoint，并配置 Server URL 和认证。[11] 这个公开路径不能等同于用户可直接添加本机 stdio 服务。云端的 `localhost` 也不是你的 Mac。

如果你使用的 Manus 桌面版本提供用户自定义本地 MCP 接入入口，并能在本机启动 stdio 子进程，就可以按本地模式适配，但此入口仍需在开发验收阶段实际确认。目前没有完成 Manus 接入实测。

如果只能使用公开文档所述 HTTPS 入口，接入会要求安全远程桥接和认证，改变“只供本地调用、一期无登录”的边界。这属于另行审批的二期，不在一期偷偷打洞或把任意命令执行服务暴露到公网。

## 8. 审批后的开发顺序和验收

建议在现有工作区新建独立项目 `local-terminal-mcp/`，不修改其他挑战工程。源码、测试和 README 按项目惯例放在该目录；测试临时文件和取证日志放入本题 `.work` 子目录，最终测试报告放入本题 outputs。不会初始化网页项目，也不会替你创建 Git 提交或发布仓库。

**第一步，验证关键机制。** 先完成最小 PTY Broker、受控 shell bootstrap 和退出码/输出边界实验。验证 `cd`、`export` 延续，交互输入不吞后续控制语句，断开网关仍可重新 link。若这些关键机制有具体失败，先修正实现；若必须改变已批范围，向你说明后再推进。

**第二步，实现完整生命周期。** 增加 link、单控制者、命令记录、幂等提交、事件日志、游标和进程回收。所有输入和操作做大小校验；普通业务错误返回明确代码，例如 `NOT_MANAGED`、`SESSION_BUSY`、`CONTROL_HELD`、`CURSOR_EXPIRED` 和 `SHELL_UNMANAGED`。

**第三步，接 MCP。** 使用 SDK v2 的双代 stdio 入口注册 9 个工具与终端事件 Resource。新旧协议测试分别保存实际使用的版本和能力；只在测试覆盖通过的范围内声明兼容，不用“采用官方 SDK”替代测试结果。

**第四步，做自动化和真实客户端测试。** 自动化覆盖以下关键验收场景，不以模拟日志代替真实 PTY：

1. 创建后 exec 短命令，验证正常和非零退出码，并验证带引号、换行、Unicode 与无末尾换行的命令输出。
2. 同一 shell 中先 `cd`、`export`，再 exec 验证状态延续；普通文本中的伪完成标记不能提前结束命令。
3. 分次输出的长任务，read 按游标连续取回；重复游标可重放，多读者不影响彼此，日志淘汰明确报告缺口。
4. 启动交互程序，先读取提示，再 write 内容并回车，取得回应；Ctrl-C 后 shell 可恢复使用。
5. 客户端 A 创建、客户端 B 按 PID link，确认 session ID 和真实进程不变；未托管 PID 和复用 PID 都不能误接。
6. 忙碌时 exec 被拒绝，两个控制者不会交错输入；解绑或断线释放控制权但不杀终端。
7. 网关重启后继续读写原终端；Broker 崩溃后返回 LOST 或 UNKNOWN，不虚报恢复，也不重复提交不确定的命令。
8. 终止运行中的普通进程树，核实没有残留受管进程；重复终止幂等，退出后的日志仍可读。
9. 支持订阅的 SDK 客户端验证长连接更新通知和增量消费；Tool-only 客户端验证长轮询降级，不把两者混称为相同能力。
10. 限额、高速输出、读取取消、磁盘失败及异常关闭不导致无限内存或错误终止其他会话；resize 对终端尺寸生效。

随后使用你本机的 Cursor CLI 做真实集成，保存工具调用证据和实际协议版本。若模型调用被登录、账户额度或宿主策略阻挡，报告为 blocked，不把协议发现通过冒充 Agent 验证通过。Manus 本地接入是否可验证单独列出结果或前置限制。

最终交付包括可运行源码、锁定依赖、构建和启动命令、Cursor 项目级示例、Tool 契约、自动化测试、真实客户端验证报告，以及明确列出的限制。测试期间只执行专用临时目录里的无害命令，并在完成后回收测试进程。

## 9. 请审批的一期范围

推荐批准以下完整边界后进入开发：本地同 UID 调用，无登录和网络监听；独立 Broker 持有 PTY，MCP 网关可重启；实现上述 9 个工具；PID link 仅限本服务托管的终端；空闲受控 shell 执行命令，忙碌前台进程通过 write 交互；标准长连接更新通知加游标读取，Tool-only 客户端使用长轮询；Cursor CLI 做实际验收，Manus 是否有可用本地入口如实核实，不承诺一期云端 HTTPS 接入。

一期不实现任意 GUI 终端接管、容器式并发 exec、Broker 崩溃后的 live PTY 复活、跨用户隔离、公网服务、launchd 自启或通用屏幕渲染。如果你要修改其中任何边界，特别是“任意 PID”或“直接分片推送”，请先补充，我会修订方案，再开始编码。
